### What the code says today (verified 2026-11-05)
- **Accounts are global and email is unique.** `ApplicationUser` has no tenant; `RequireUniqueEmail = true` (`Extensions/ServiceCollectionExtensions.cs:131`). **At most one Active membership per account** is enforced in the database (`IX_TenantMemberships_UserId_ActiveUnique`, `TenantMembershipConfiguration.cs:54`), and `CustomerContextResolver` refuses zero or several. Every acceptance path refuses an address that already has an account (`ExistingAccountConflict`). So **one person cannot belong to two companies**, and SSO keeps it that way.
- **Sign-in** `POST /api/identity/auth/login` (`Controllers/AuthController.cs:53`) has no tenant step. It calls `VerifyHashedPassword(user, user.PasswordHash!, …)`, which **throws on an account without a password**. That is a 500 today and must become 401 once provider-only accounts exist. Refresh rotates single-use tokens; logout revokes all of them. Refresh tokens are stored **in plain text** (`RefreshToken.Token`, unique index), so that goes on the board.
- **Sessions** come from `IAuthSessionFactory.CreateAsync(user)` (`Features/Accounts/AuthSessionFactory.cs`): a 60-minute HS256 JWT (`TokenService`) carrying tenant, membership, `MembershipAccessRevision`, employee and permissions, plus a 7-day refresh token. View-as tokens get no refresh token.
- **Gateway** `TenantAuthorityGateMiddleware` checks the membership revision on each authenticated request. The `identity-route` has no authorization policy, so anonymous `/api/identity/sso/*` needs no gateway change. Bumping `TenantMembership.AccessRevision` ends access tokens on the next request (401 `revision-stale`).
- **Shell `/api` proxy** (`apps/shell/src/app/api/[...path]/route.ts`) passes 302s through (`redirect: "manual"`) but copies headers with `headers.set`, which **keeps only the last `Set-Cookie`**. This must become `append`. It strips `host`, so Identity must build URLs from config, never from the request.
- **Invitations**: workforce `POST /api/identity/invites/{token}/accept` → `WorkforceInvitationAcceptanceService` (selector/digest credential, row locks, creates the account with a password, returns `UserDto` and **no session**; the core page at `apps/core/src/app/invite/accept` then logs in). Administrator `AdministratorInvitationAcceptanceController` → `AdministrativeInvitationAcceptanceService` (also recovery). First administrator `TenantActivationController` → `BootstrapActivationService`. The shell's three administrator journeys share `apps/shell/src/app/activate-invitation/activate-invitation.tsx` (`lib/activation.ts`). All four acceptance services require a password and call `userManager.CreateAsync(account, password)`.
- **Adding an administrator** asks for the caller's password (`TenantAccessController.cs:124`), and candidates must have a `PasswordHash` (`:161`, `TenantAccessProjection.cs:501`). Provider-only people would be shut out of both.
- **Branded sign-in** is `?company=<slug>` or the last company stored on this browser (`packages/auth/src/sign-in-brand.ts`, public `GET /api/identity/brand/companies/{slug}`). `SignInPage` (`packages/auth/src/components/signin-page.tsx`) has a dead "SSO" button, a dead "Forgot password" link and an unused "Remember me".
- **Settings › Sign-in** (`apps/core/src/features/settings/sections/sign-in.tsx`) edits CoreHR provisioning settings, gated by `settings.provisioning.view/manage`. **People › Sign-in** comes from `PeopleSignInDto(State, At)` (CoreHR, from Identity's workforce-account statuses).
- **Audit**: `AccessAuditEvent.Create(tenantId, actor…, action, resourceType, resourceId, summary, before, after, correlation)`, tenant-scoped.
- **Tests**: `IdentityApiFactory` (environment `Testing`, in-memory) and `RelationalTestDatabase` (Postgres). Latest migration `20261031120000_SplitPersonalDetailsKeys`.

### Decisions (with reasons)
1. **Identity runs the code flow itself, built on Microsoft.IdentityModel primitives.** The orchestration is hand-written; discovery and JWKS come from `ConfigurationManager<OpenIdConnectConfiguration>` and validation from `JsonWebTokenHandler`. Why not the ASP.NET OIDC handler: it assumes static schemes and a cookie sign-in, while we need per-company providers created at runtime, four purposes (sign-in, invitation, test, confirm), Fusion's own token pair, and a backchannel guarded against SSRF. After the exchange, `IAuthSessionFactory` mints the usual pair, so the gateway, revisions, refresh and view-as are unchanged.
2. **Authorization code + PKCE (S256) + state + nonce, confidential client, `response_mode=query`.** Lax cookies survive a top-level GET; Entra's `form_post` would drop them. Allowed algorithms: RS256/ES256 only. Validate `iss`, `aud`, `azp`, `exp`/`iat` (2-minute skew), `nonce`; the RFC 9207 `iss` parameter when present; discovery's `issuer` must equal the configured issuer.
3. **Mix-up defence: one callback path per provider.** `/api/identity/sso/callback/microsoft`, `/google`, `/c/{connectionId}`. The flow stores provider and issuer and is refused on another path (RFC 9700 §4.4).
4. **Browser binding and handoff without secrets in URLs.** `POST /sso/flows` (a fetch) creates the flow, sets an httpOnly `SameSite=Lax` cookie (`fusion_sso`, path `/api/identity/sso`, 10 minutes, `Secure` when the public origin is https; the flow stores only its SHA-256), and returns `authorizeUrl`. The page then navigates there. The callback checks cookie and state, does the work, stores the result on the flow and redirects to a shell page. That page `POST`s `/sso/result` once to collect the session. No token, code or id ever goes in a redirect. One rule for every purpose; the authenticated purposes (test, confirm) need the bearer token, which a navigation can't carry.
5. **Identities are keyed by provider + issuer + subject.** Microsoft uses `oid` (with `tid` inside `iss`), others use `sub`. A link wins over email, so an email change at the provider moves nothing. A different subject presenting a linked address is refused.
6. **Which email can be trusted, per profile** (only for the first link or an invitation):
   - **Google**: `email_verified` must be true, and the address must be `@gmail.com` or carry `hd` equal to its domain (Google: `email` isn't a stable identifier).
   - **Microsoft (Fusion-wide)**: work or school accounts only (`organizations`); the consumer `tid` `9188040d-…` is refused; the `xms_edov` optional claim must be true (Microsoft: `email` is mutable and unverified).
   - **Company Entra**: `tid` must equal the configured directory; take `email`, else `preferred_username` (Entra only allows verified UPN suffixes); guests (`idp` ≠ `iss`) are refused.
   - **Company OIDC**: `email_verified` must not be false; with issuer `accounts.google.com`, `hd` must also match.
7. **Only invited people, and an invitation is accepted only from its link.** Provider sign-in finds a linked account or an account with that trusted email, else refuses (`no_account`) and creates nothing. Invitations are completed through the provider only from the invitation page: the flow carries the invitation's kind and credential (Data Protection-encrypted on the flow), and the trusted email must equal the invited one. The existing acceptance services run with an external login instead of a password (`CreateAsync(account)` without a password, link in the same transaction), then a session is issued. Why not "pending invitation found by email": holding the link is the proof of invitation, and email alone through a public provider is weaker.
8. **Who vouches for whom.** A company's connection reaches only accounts whose Active membership is in that company and whose address is in one of its **proved** domains. Fusion-wide Microsoft and Google reach anyone, unless the account's company switched that provider off or requires its own provider for the account's domain. Platform operators never sign in through a provider (refused, `operator`).
9. **Proving a domain without DNS (rung 2).** A domain is proved when a **successful test sign-in through the company's tested connection** returns a trusted address in it. Public mail domains are refused from a list (gmail.com, outlook.com, hotmail.com, yahoo.com, icloud.com, live.com, aol.com, proton.me, gmx.*, yandex.*). A domain can be proved by only one company (filtered unique index); an unproved entry blocks nobody. Why this is enough: a claim only routes the sign-in page and enforces **on the company's own members**, so a false claim can't reach or lock out another company. DNS TXT proof is a later rung (a board note) for hosted use.
10. **The requirement is one switch per company, covering all its proved domains.** Turning it on needs: a tested connection, at least one proved domain, the actor's own link to this connection used within 15 minutes (they just got in that way), and **at least one usable administrator with a password**. In those domains, password sign-in works only for that company's usable administrators (the user's choice). Microsoft and Google are refused for those members. Workforce invitations there accept only through the company's provider; administrative invitations (bootstrap, administrator, recovery) still accept a password.
11. **Existing sessions end at once** (the user's choice). In the transaction that turns the requirement on (or proves a domain while it's on), affected members who aren't administrators have their **password-method** refresh tokens revoked and their membership `AccessRevision` bumped. Provider sessions refresh as usual. Refresh also refuses a password-method token for someone who must now use the provider. `RefreshToken.Method` records how a session started and is carried across rotation.
12. **Step-up confirmation.** Sensitive actions accept `{ password }` or `{ sso: true }`. The latter is a Confirm flow with `prompt=login` and `max_age=0`, `auth_time` after the flow started, by the same user, under 5 minutes old, used once. It covers: adding an administrator (which today needs a password), saving, changing or removing the connection, turning the requirement off, removing a proved domain, and setting a password when the account has none. "Can be made administrator" becomes "signs in" (a password **or** a link).
13. **Way back in** (the user's choice): administrators keep a password. Settings shows which administrators have one; an administrator without one can set it (confirmed through the provider). The requirement can't turn on without at least one. Platform recovery is unchanged, since a company with usable administrators isn't eligible.
14. **Secrets.** Company client secrets are encrypted with ASP.NET Data Protection (`PersistKeysToDbContext<AppIdentityDbContext>`, application name `Fusion.Identity`, protector `Fusion.Identity.Sso.ClientSecret.v1` with the tenant id as a sub-purpose, so ciphertext moved to another company won't decrypt). Never returned (only "set on <date>"), never logged; the flow's invitation credential and PKCE verifier are protected the same way. Fusion-wide credentials come from configuration (`Sso:Microsoft:*`, `Sso:Google:*`, via `stack.ps1` from the `FUSION_SSO_*` user variables). Hosting later must protect the key ring with a certificate or a key vault.
15. **SSRF guard on every outbound provider call** (discovery, JWKS, token). Https only; one `SocketsHttpHandler` whose `ConnectCallback` resolves the host and refuses loopback, private, link-local, CGNAT, multicast and metadata addresses at connect time (DNS rebinding safe); no redirects; 5-second timeout; 256 KB response cap. The single exception, in Development and Testing only: the exact prefix `{Sso:PublicOrigin}/api/identity/dev-oidc/`.
16. **Test provider** (`/api/identity/dev-oidc/{microsoft|google|company}`: discovery, JWKS, authorize form, token), mapped **only** when `IsDevelopment() || IsEnvironment("Testing")`. It signs with an in-memory RSA key, issuers mirror the real shapes (Microsoft `…/microsoft/{tenantid}/v2.0`), and the client secret must equal `Sso:TestProvider:ClientSecret` (so a wrong-secret test fails truthfully). In Development the Fusion-wide Microsoft and Google settings and the Entra authority point at it unless real credentials are set. That way the real buttons work on localhost.
17. **Public origin from config** (`Sso:PublicOrigin`, `http://localhost:3000` in Development, required elsewhere). Redirect URIs and landing pages are built from it; `returnTo` is kept server-side and must be a relative path (not `//`).
18. **Several companies**: unchanged (one account, one Active membership). Refusals say "This address already has a Fusion account" as today.
19. **Who manages it**: viewing the block needs `settings.provisioning.view`; every SSO write needs a **usable tenant administrator** (`UsableTenantAdministrator`), checked on the server. Writes are refused in view-as (`ReadOnlyViewMiddleware`, and flows are POSTs).

### Threat model
| Threat | Defence |
|---|---|
| Takeover through an unverified or changed email | Per-profile trust rules (D6); link by issuer + subject wins (D5); same address with a different subject refused; `xms_edov`, `email_verified`/`hd`; invitations only from the link with an exact address match (D7) |
| One company's provider vouching for another's people | A connection reaches only its own Active members in its proved domains (D8); unique proved domains; Entra `tid` pinned; per-connection callback paths |
| Replayed or stolen provider returns | State bound to an httpOnly cookie (hash on the flow), single use, 10 minutes; PKCE S256; nonce; result collected once by POST with the cookie; no secrets in URLs; per-provider callbacks against mix-up; `iss` parameter check |
| Login CSRF and session swapping | Flow cookie plus state; `SameSite=Lax`; result POST needs the cookie |
| Locking a company out | Requirement needs a fresh own sign-in through it and an administrator with a password; administrators keep passwords; issuer and client can't change while it's on (secret can); Fusion operators unaffected |
| SSRF through the issuer URL | D15 guard at connect time, no redirects, size and time caps; discovery `issuer` equality |
| Secrets leaking | Data Protection with a tenant sub-purpose; never in responses or logs (test asserts); invitation credential and PKCE verifier protected on the flow; flows purged after a day |
| Test provider reaching production | Mapped only in Development/Testing; profiles from config; SSRF guard refuses loopback elsewhere; a Production-environment test proves 404 and refusal |
| Account enumeration | `discover` answers by domain, never by account; required-domain password failures return the same 401 |
| Brute force on anonymous endpoints | ASP.NET rate limiter on `flows` and `discover` (30 per minute per IP) |

### Domain model and migration `AddSingleSignOn` (schema only)
- `SsoConnection` (ITenantEntity; one per tenant, unique `TenantId`): `Kind` (MicrosoftEntra | OpenIdConnect), `DisplayName`, `Issuer`, `EntraTenantId?`, `ClientId`, `ProtectedClientSecret`, `SecretSetAt`, `Status` (Draft | Tested), `LastTestAt/ByUserId/Outcome/Email/Message`, `RequiredAt?/RequiredByUserId?`, created/updated stamps, `Version` (xmin).
- `SsoDomain` (ITenantEntity): `ConnectionId`, `Domain` (lowercase, IDN as punycode), `ProvedAt?`, `ProvedByUserId?`. Unique (TenantId, Domain); filtered unique (Domain) WHERE ProvedAt IS NOT NULL.
- `ExternalLogin`: `UserId`, `Provider` (microsoft | google | company), `ConnectionId?`, `Issuer`, `Subject`, `EmailAtLink`, `LinkedAt`, `LastUsedAt`. Unique (Provider, ConnectionId, Issuer, Subject) and (UserId, Provider, ConnectionId).
- `SsoFlow`: `BindingHash`, `Purpose` (SignIn | Invitation | Test | Confirm), `Provider`, `ConnectionId?`, `ExpectedIssuer`, `State`, `Nonce`, `ProtectedCodeVerifier`, `InvitationKind?`, `ProtectedInvitationCredential?`, `ActorUserId?`, `LoginHint?`, `ReturnTo`, `CreatedAt`, `ExpiresAt`, `CompletedAt?`, `ResultUserId?`, `ResultCode?`, `ResultJson?`, `ConsumedAt?`. Expired rows purged on write.
- `Tenant.AllowMicrosoftSignIn`, `Tenant.AllowGoogleSignIn` (default true). `RefreshToken.Method` (varchar 64, default `password`). `DataProtectionKeys` table.

### Tests (Identity.Tests › `Features/SingleSignOn/`, plus the noted others)
- **Flow security**: callback without the cookie, with another flow's cookie, or with the wrong state → refused; the same callback twice → second refused; `result` twice → second 404; flow past 10 minutes → `expired`; nonce, aud, iss or exp wrong, or `alg` none/HS256 → `provider_failed`; callback path of connection X for a flow of Y → refused; RFC 9207 `iss` mismatch → refused; every callback `Location` free of tokens and codes; `returnTo` `https://evil`/`//evil` → `/`; Production-environment factory: `dev-oidc` 404 and a loopback issuer refused.
- **Sign-in**: linked identity signs in (refresh `Method` set); first trusted email links (audit); Google unverified, non-gmail without `hd`, `hd` mismatch → refused; Microsoft without `xms_edov` or with the consumer tenant → refused; unknown address → `no_account` with user and membership counts unchanged; same address, different subject → `linked_to_someone_else`; email changed at the provider for a linked subject → same account; operator → `operator`; suspended membership or inactive account → refused; company switched Google off → `provider_off`; login of an account without a password → 401, not 500.
- **Invitations**: workforce via provider → account without password, membership, binding, link, Accepted, session; mismatched address → `invitation_mismatch` with the invitation still Pending; administrator invitation and first activation via provider; existing account → `existing_account`; required domain: password acceptance `sso_required`, Fusion-wide → `company_requires`, company provider → accepted; concurrent double acceptance (relational) → one account.
- **Settings authorization and isolation**: a non-administrator holding `settings.provisioning.manage` → 403 on every write; a viewer gets GET with `canManage` false; company B's administrator sees only B, and A's connection, domain and link ids → 404; the secret never appears in any response body; A's ciphertext copied to B's row fails to decrypt; writes in view-as refused; SSRF: `http://`, `127.0.0.1`, `169.254.169.254`, `10.0.0.5`, a host resolving to private, and a redirecting discovery → refused with no request reaching the private address; discovery issuer mismatch → refused.
- **Domains**: public mail refused; proved elsewhere → refused; a test sign-in proves a listed domain; a test identity outside the list proves nothing; A's connection can't sign in B's member even if B's domain is listed (unproved) on A.
- **Requirement**: turning on refused when untested, with no proved domain, without a fresh own link, or with no administrator who has a password. On: non-administrators' password refresh tokens revoked and revision bumped, provider sessions and administrator password sessions survive. After: a member's password login → 401, an administrator's password works (and is audited), a password-method refresh → `sso_required`, Google → `company_requires`, the company provider works, another company's member in the same domain is unaffected. Turning off needs confirmation. Changing the issuer while on → 409; replacing the secret while on → allowed.
- **Confirmation**: adding an administrator with provider confirmation and no password works; reused, someone else's, or older than 5 minutes → refused; a provider-only person can be made administrator.
- **CoreHR**: `PeopleSignInDto.Methods` flows through (contract test). **Frontend**: sign-in steps per `discover` answer and error code; complete page success and refusal; proxy forwards two `Set-Cookie` headers; activation page provider choices; settings block consequence and preconditions.
