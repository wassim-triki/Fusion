## Diagnosis

Core hard entry and authenticated refresh reproduce generic access placeholder → page-owned data skeleton → content. Warm list-to-detail and back/forward do not replay the access hold. The current Core access boundary does **not** use the route registry; the historical registry comment describing `CoreSetupRouteGuard` is stale. The old setup-query gate is not today's cause on the tested routes.

Three Core controls establish ownership:

- Hold all external scripts: server HTML already contains the stable module frame and generic `Checking Core HR access` placeholder, with no mounted page query. Releasing scripts allows hydration/session restoration and the switch.
- Hold only the profile API: generic access placeholder still ends and `WorkerProfileSkeleton` appears **before** that request is released. The API controls how long the profile skeleton lasts, not why the earlier generic appears.
- Hold only tenant-summary: profile including its subsections reaches zero skeletons before tenant-summary is released. Access resolves from restored claims, independently of that request.

Performance reproduces the same hard-entry/refresh pattern on `/performance/one-on-ones` and its series record. Its shared access hook is identical to Core's. Warm list → series reused a series query already started by the list's `NextUp`; only a local sidebar placeholder appeared. Back/forward used the retained client/query state and did not replay access loading.

Shell → Performance and Performance → Shell are **document navigations**, not one persistent React app handing off a child. The shared sidebar renders module and Home links as anchors. Network evidence contains a new document request; `performance.timeOrigin` resets. The destination creates a new AuthProvider and QueryClient, so browser asset warmth does not preserve the old MFE's data cache. Server rewrites proxy the target MFE document; Shell's React `app/loading.tsx` is not inserted around Core/Performance documents.

Performance Overview is a useful negative control: `Checking Performance access` → page-owned `Loading Performance` → page-owned `Loading Overview` all use the same six skeleton blocks (`PageSkeleton rows={4}`). Different labels/owners do not necessarily mean a visible shape mismatch. Its `useWorkspaceContext` then enabled `useOverview` explain the latter two stages.

Shell Home has a separate confirmed sequence: a single centred block (`ShellEntrySkeleton`, no AppShell) → mounted `FusionHome`/AppShell with local query placeholders → content. The whole frame mounting at auth readiness is real, but is not caused by an MFE's route registry. The pending branch is directly in Shell `app/page.tsx`; its generic six-card root `loading.tsx` is another possible owner, not the one identified in these Home captures.

History caveat: repository Playwright 1.61.1 launches headless Chromium with `--disable-back-forward-cache` by default (verified process arguments). Cross-document back/forward repeats readiness in that mode. Repeated the crossing with that argument removed; `pageshow.persisted` was still false and document requests occurred on both history traversals. Therefore these runs prove **history reloads**, not restoration of a frozen document. A genuinely BFCache-restored document remains unverified; do not infer that all browser history must remount authentication.

Shell settings are a negative control for the customer-MFE access placeholder: Preferences shows its real page without a generic access stage; Notifications shows its own `SettingsSkeleton` inside `SettingsFrame`. Settings navigation and history **also request documents**, because the shared settings sidebar uses anchors when `basePath` is empty. Do not label that case soft navigation merely because both URLs belong to Shell. On some entries a brief DOM stage matches Shell's root six-card `loading.tsx` (one outer `animate-pulse`, geometry `[96,48,1248,568]`, no main/frame), e.g. 3.491–3.518s on fresh Preferences. That 27ms DOM stage was not resolved as six cards in the screencast; treat its visual salience as unproven. It is distinct from the repeatedly visible Home entry block.

Both list/detail hard entries and refreshes reproduce. Warm list → record shows its record skeleton directly; back/forward retains data without an access hold. `staleTime: 0` on tenant detail means revalidation, not deletion of cached data and compulsory skeleton replay.

The readiness hold is intentional; the disagreement between its presentation and the target page is the defect. Core and Performance share the readiness mechanism, while Platform independently repeats the presentation pattern. Shell Home's late frame mount is a separate local branch, not the same registry bug.
